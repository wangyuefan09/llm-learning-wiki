# RAG项目面试问答

## 回答原则

- 先讲当前源码事实，再讲设计取舍。
- 自动化测试通过不等于真实业务效果已经得到证明。
- 项目职责围绕真实需求、设计、代码路径、测试和取舍展开。
- 没有真实评估、压测或故障记录时，明确写“待验证”。

## 项目介绍

### 请介绍一下这个项目

回答：

> 这是我独立设计并实现的风电领域本地知识库项目，主要服务于风电设备、运维和故障诊断资料的检索问答。用户通过 API 上传 PDF、DOCX、Markdown 或 TXT 文档，系统完成结构化解析、章节感知切分、表格语义切分、Embedding 和 OpenSearch 索引。查询时同时执行 BM25 和 HNSW 向量检索，再通过 RRF 融合。项目提供普通 RAG、流式 RAG 和七节点 Agentic RAG，并通过 Langfuse 记录请求和节点观测。文档侧还实现了内容哈希去重、状态机、处理租约、重新索引版本切换和可恢复删除。

### 这个项目的数据从哪里来

回答：

> 当前只接收人工上传的风电文档，不包含自动抓取或定时采集流程。这样可以把工程重点放在文档解析、索引、检索、生成和状态管理上，也避免把与业务主链路无关的数据采集代码留在项目中。

### 为什么要做这个项目

回答：

> 风电技术资料通常分散在设备手册、检修 SOP、故障案例和告警说明中，既有自然语言描述，也有故障码、型号和复杂表格。单纯关键词搜索难以处理同义表达，单纯向量检索又容易漏掉精确术语，所以我实现了一个同时支持文档结构、表格、业务字段过滤和混合检索的知识库，并进一步用 Agent 工作流处理证据评分和 Query Rewrite。

### 你在项目中负责什么

回答：

> 我负责项目的整体架构和端到端实现，包括文档上传与解析、内容哈希去重、中文章节感知切分、表格双存储、Embedding、OpenSearch Mapping、BM25 与 HNSW 的 RRF 融合、风电 metadata 和权限过滤、普通与流式 RAG、七节点 Agentic RAG、Langfuse 观测，以及 reindex、删除租约和补偿恢复。我也为这些核心链路补充了静态检查、单元测试和覆盖率门禁。

## 文档解析与表格

### 为什么选择Docling

回答：

> 项目需要处理 PDF、DOCX、Markdown 和 TXT。PDF 和 DOCX 的布局、扫描页和表格更复杂，因此使用 Docling；Markdown 和 TXT 使用轻量解析器。所有解析器统一返回 `sections`、`raw_text`、`tables`、`figures` 和 `metadata`，下游切分与索引不需要感知原文件格式。

### PDF是如何解析的

回答：

> 系统先校验文件大小、文件头和页数，再调用 Docling 做布局和表格结构解析。OCR、布局模型、表格模式和阅读顺序后处理都可以配置。下游优先使用文档树顺序；检测到双栏时再结合位置信息重排，最后构建统一的章节、全文和表格结构。这个设计已经落到代码，但双栏、扫描件和跨页表格准确率仍要用真实样本评估。

### tables如何进入向量库

回答：

> 表格走两条链路。第一条把原始 rows、Markdown 和 HTML 按 `doc_id + version + table_id` 存入 PostgreSQL；第二条通过 `TableChunker` 重复文档标题、表题和表头，把每行展开成“列名=值”的语义文本，生成 `chunk_type=table` 的切片写入 OpenSearch。检索靠语义文本，回答需要精确结构时再回查 PostgreSQL 中的活动版本表格。

### 如何避免表格正文重复索引

回答：

> 解析后会从 sections 和 raw_text 中移除已经识别出的表格 Markdown/HTML，再分别生成正文切片和表格切片，降低同一表格内容被重复向量化的概率。

## 文本切分

### 项目的切分逻辑是什么

回答：

> 上层优先按 section 编排。连续短 section 会合并，长 section 会继续递归拆分；没有有效 section 时回退到 raw_text。切片会重复文档标题和章节标题，并设置 6000 字符硬上限。底层当前只保留 LangChain 的 `RecursiveCharacterTextSplitter`。

### chunk_size和overlap的单位是什么

回答：

> 当前默认 `chunk_size=800`、`overlap=100`，使用项目自定义的启发式长度函数。中文字符和标点按单元计数，英文按词计数，其他字符做近似折算。因此它比按空格分词更适合中文，但不是目标模型 tokenizer 的严格 Token 数。面试时不能直接说“800 个模型 Token”。

### 为什么增加max_chunk_chars

回答：

> 启发式长度估算可能在异常长字符串、无分隔符文本或复杂符号中低估真实长度。`max_chunk_chars=6000` 是独立的字符硬上限，用来保护 Embedding 输入、索引字段和下游 Prompt，不让估算误差导致失控大块。

### 是否评估过chunk质量

回答：

> 当前已经有中文、英文、中英混合、短章节合并、长文本和字符硬上限的单元测试，但还没有正式的真实文档分布和检索增益报告。下一步要统计 chunk 数量、长度 P50/P90/P99、fallback 比例，并用标注问题比较不同参数的 Recall@K、MRR、延迟和索引体积。

## Embedding与OpenSearch

### 项目使用什么Embedding模型

回答：

> 项目不绑定具体模型，支持 Jina 或 OpenAI-compatible provider。模型名称、接口和维度通过运行配置注入，示例维度是 1024。无论选择什么模型，都必须保证文档与 query 使用兼容向量空间，并让 OpenSearch Mapping 维度与实际输出一致。

### 为什么不把某个模型写死

回答：

> 模型选择应该由风电评估集决定，而不是写死在业务代码中。配置化后可以在不改主链路的情况下重建索引，对比不同模型的召回、延迟和成本。但更换模型或维度仍然需要全量重算历史向量和建立新索引。

### 为什么选择OpenSearch

回答：

> 项目同时需要中文全文检索、HNSW 向量检索、字段过滤、权限过滤和 RRF 融合。OpenSearch 可以在同一系统中完成这些工作。PostgreSQL 负责事务性文档元数据、状态机和表格原始结构，OpenSearch 负责可检索切片，两者职责不同。

### 当前Mapping有哪些关键字段

回答：

> 标识和版本字段包括 `chunk_id`、`doc_id`、`kb_id`、`version`、`status`；风电字段包括文档类型、风场、风机型号、部件和故障码；表格字段包括 `chunk_type`、`table_id` 和行范围；安全与溯源字段包括 `permission_ids`、源文件名和内容哈希。正文、标题和章节使用 CJK analyzer，故障码、型号和部件使用 keyword。

### Mapping不兼容怎么办

回答：

> 应用启动会校验 schema version、表格字段类型、向量字段类型和维度。不兼容时明确失败，不自动删除索引。开发环境可以重建；正式环境应创建新索引、全量写入和验证，再通过配置或别名切换，不能直接删除现有索引。

### HNSW核心参数是什么

回答：

> `m` 控制图连接规模，`ef_construction` 控制建图时的候选范围，`ef_search` 控制查询时的搜索范围。当前 Mapping 配置 `m=16`、`ef_construction=512`，没有把某个 `ef_search` 值写成已调优结论。

## 检索链路

### 项目的检索链路是什么

回答：

> 查询先按可信访问上下文和业务字段构建过滤条件。启用混合检索时生成 query embedding，同时执行 BM25 和 HNSW，再通过 OpenSearch search pipeline 做 RRF。Embedding 失败可以回退 BM25；OpenSearch 执行失败则返回明确的 503，而不是伪装成正常零结果。

### 为什么使用RRF而不是加权平均

回答：

> BM25 分数和向量相似度不在同一尺度，加权平均需要先归一化并通过评估集调权重。RRF 只依赖两路候选中的排名，适合作为初始稳定方案。当前 pipeline 使用 `rank_constant=60`，但是否优于加权融合仍需实验。

### 项目是否有Reranker

回答：

> 当前没有独立 Cross-Encoder Reranker。普通 RAG 使用 RRF 后的结果；Agentic RAG 还会用 LLM 逐条判断证据相关性。RRF 是排名融合，LLM 评分是过滤和路由，二者都不等同于专用 Reranker。

### 如何判断是Embedding问题还是chunk问题

回答：

> 如果召回主题正确但证据总缺上下文，或者一个块混入多个主题，更像 chunk 问题；如果块本身完整，但同义表达持续召回不到，更像 Embedding 领域适配问题。排查时还要检查 query 改写、metadata filter、权限过滤、索引版本和 RRF 候选，不能只看最终答案。

## 文档状态、并发与恢复

### 如何防止重复入库

回答：

> 系统对文件内容计算 SHA-256，并在 PostgreSQL 上建立 `(kb_id, content_hash)` 唯一约束。应用层先查询已有记录，真正的并发冲突由数据库唯一约束裁决。`ready` 返回原记录，`failed` 可以取得租约重试，`deleted` 可以恢复原记录重新入库。

### 为什么需要processing token和租约

回答：

> 单纯使用 `processing` 状态无法区分任务仍在执行还是进程已经中断。token 表示当前处理者，过期时间允许新任务通过数据库 CAS 接管。完成、失败和补偿都必须匹配 token，因此旧任务恢复执行后也不能覆盖新任务状态。

### reindex如何避免新旧版本混乱

回答：

> reindex 先取得跨进程租约，把新版本写成 staging，校验 Embedding 数量、批量写入数量和目标切片数量，再切换 ready 状态并检查其他版本是否仍为 ready，最后更新数据库活动版本和清理旧版本。失败时删除目标版本并恢复旧版本。它是可验证切换和补偿回滚，不是跨 PostgreSQL、OpenSearch 的严格分布式事务。

### 删除为什么要先进入deleting

回答：

> 如果直接删除数据库记录，OpenSearch 残留切片可能继续被检索。当前流程先通过 CAS 抢占 `deleting`，把所有切片下线并确认 ready 数量为零，再更新为 `deleted`、物理清理切片和源文件。删除也有 token 和租约，进程中断后可以接管过期状态继续执行，旧任务不能覆盖新任务。

## 权限

### 当前权限过滤做到什么程度

回答：

> 查询前过滤已经实现。公开问答、检索 API 和 Gradio 强制使用公开访问上下文，只能召回没有权限标记的文档；问答和检索请求模型不接受客户端提交权限 ID；缓存键也包含内部访问上下文，避免跨权限复用回答。文档上传元数据虽可以写入 `permission_ids`，但它不会让上传请求获得对应的查询权限。

### 是否已经完成多租户认证

回答：

> 还没有。`trusted/admin` 只是供未来认证层使用的内部对象。当前没有登录、用户身份映射、角色管理和管理接口保护，因此不能把现有过滤器描述成完整权限系统。

## Agentic RAG

### 项目有哪些Agent节点

回答：

> 当前有七个节点：`guardrail`、`out_of_scope`、`retrieve`、`tool_retrieve`、`grade_documents`、`rewrite_query` 和 `generate_answer`。提示词、检索工具、metadata 和返回来源字段都按风电场景设计。

### 什么条件下改写query

回答：

> 检索结果为空，或者 LLM 文档评分后没有相关证据时，路由到 `rewrite_query`。改写节点基于原始问题补充风电设备、运维和故障诊断表达，再进入下一轮检索。

### 如何防止无限循环

回答：

> 状态中记录 `retrieval_attempts`，默认最大次数为 2。达到上限后 `retrieve` 不再创建工具调用，而是返回中文证据不足提示并结束。当前还可以进一步增加总耗时和 Token 预算。

### 为什么没有网页搜索

回答：

> 当前项目定位是本地风电知识库，优先把内部文档解析、权限和检索链路做完整。网页搜索会引入来源可信度、时效性、网页解析和提示注入问题，因此当前明确列为未实现能力，不在面试中说成已有功能。

## Langfuse与评估

### 为什么引入Langfuse

回答：

> Agentic RAG 包含守卫、检索、评分、改写和生成，普通日志很难还原一次请求的完整路径。Langfuse 用 trace 串起请求，用 span 或 generation 记录具体步骤，可以定位问题来自 Embedding、检索、路由、改写还是生成。

### 检索失败如何观测

回答：

> 正常零结果仍是成功检索，只记录返回数量；OpenSearch 基础设施异常会抛出 `SearchExecutionError`，接口返回 503，同时把检索 span 标记为 `ERROR`，记录 `success=false`、异常类型和耗时。

### feedback如何设计

回答：

> Agentic 接口返回 `trace_id`，前端可以把评分和评论提交到 `/feedback`，后端按 trace 写入 Langfuse。之后可以从差评反查完整链路，判断根因是召回、评分、改写还是生成。

### 是否已经使用Ragas

回答：

> 还没有。当前项目没有 Ragas 依赖、正式评估集和离线评估脚本。自动化测试验证的是代码行为，不等于检索质量。下一步要建立风电问题集和相关 chunk 标注，再比较不同版本。

### 你会如何评估整个RAG系统

回答：

> 我会把评估拆成文档解析、chunk、检索、生成和 Agent 五层。解析层检查阅读顺序、表格结构和 sections 缺失；chunk 层统计长度分布、fallback 比例并抽样语义完整性。检索层使用带相关文档或 chunk 标注的风电问题集，用 Recall@K、MRR 和 nDCG@K 对比 BM25、纯向量和 RRF。生成层关注 Faithfulness、Answer Relevance、Correctness、完整性和引用正确性。Agent 还要评估守卫误判、Query Rewrite 的检索增益、证据误删率、检索次数、延迟和 Token 成本。

### Recall@K、MRR和nDCG分别解决什么问题

回答：

> Recall@K 衡量 Top-K 覆盖了多少已标注相关证据；MRR 只关注第一个相关结果的排名，适合一条核心证据就可以回答的场景；nDCG 同时考虑相关程度和排名位置，适合完全相关、部分相关等分级标注。它们回答的问题不同，不能用单一指标代替。

### 如何判断错误来自检索还是生成

回答：

> 先检查正确证据是否进入 Top-K。如果没有进入，继续排查解析、chunk、Embedding、BM25、filter、索引版本和 RRF；如果已经进入 Top-K，再检查是否被 Agent 文档评分节点误删。证据最终已经进入 Prompt 但答案仍错，才主要排查上下文组织、Prompt 和 LLM 生成。

### 如何评估Query Rewrite是否有价值

回答：

> 对同一批触发改写的问题比较改写前后 Recall@K、MRR、正确证据排名、延迟和 Token，同时检查新 query 是否偏离用户意图。如果改写只让表达更专业，但检索指标没有提升，只增加了模型调用和耗时，就不能认为它有正收益。

### 为什么不能只使用LLM自动评分

回答：

> LLM Judge 会受评估模型、Prompt、表达风格和领域知识影响，同一模型生成和评分还可能存在自我偏好。我会使用确定性检索指标和系统指标作为基础，用结构化 LLM Judge 批量评估开放式答案，再对风电专业术语、复杂表格和分歧样本人工复核。

## 测试、规模与性能

### 当前测试做到什么程度

回答：

> 当前项目版本的格式、静态检查和自动化测试套件通过：214 个测试通过、7 个条件式或手工测试跳过，源码覆盖率 82.49%。测试覆盖文档状态机、租约接管、表格、权限过滤、OpenSearch Mapping、检索异常、Agent 路由和 Langfuse API。但本轮没有启动真实外部服务，所以不能把该结果说成端到端部署已经验收。

### 生产数据量有多大

回答：

> 当前没有真实生产数据规模和容量报告。我不会把估算当成项目事实。面试前需要统计原始文档数、chunk 数、向量体积、HNSW 索引占用、检索延迟和端到端 P95。

### 项目遇到过哪些瓶颈

回答：

> 目前可以从设计上分析高维向量、chunk 数量、HNSW 内存、Embedding 和 LLM 延迟风险，但“实际遇到过”必须对应真实日志、trace 或压测。没有证据时只讲风险和验证方案，不虚构生产故障。
