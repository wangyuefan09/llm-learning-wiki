# Agent项目复盘

## 一句话介绍

这是一个面向企业复杂任务处理场景的通用 AI Agent 智能工作台。我参与了 Agent 运行循环、上下文与工具编排、多环境工具执行、多 Agent 协作、长期记忆、项目隔离和扩展机制等能力建设，让智能体能够把自然语言任务拆成步骤，调用浏览器、Linux 桌面、文件编辑、代码执行、文档查询等工具，并在执行过程中持续接收工具结果、调整后续动作，直到完成任务。

## 项目背景与目标

普通对话产品以“用户提问—模型回答”为主，难以稳定完成需要多步骤、多工具和长时间上下文的任务。项目希望把模型能力扩展到真实工作环境，形成统一的任务执行平台：

- 支持多轮对话、任务拆解、工具选择、结果回填和继续决策；
- 让 Agent 能操作网页、Linux 桌面、工作区文件和命令行程序；
- 用子 Agent 分担长链路任务，减少主 Agent 上下文压力；
- 用短期历史、长期向量记忆和项目知识维持跨轮次连续性；
- 通过 Project、Skills、Plugin、MCP 和 Agent Profile 支持不同业务快速接入；
- 通过运行日志、历史持久化、上下文压缩和工作区快照提高可观测性与可恢复性。

## 我的项目职责

- 参与 Agent 平台基础能力建设，围绕 `AgentContext`、`Agent.monologue()`、Prompt 组装、模型调用、工具分发和结果回填打通完整执行闭环；
- 参与多环境工具接入，将浏览器自动化、Linux 桌面、文件编辑、代码执行和文档查询纳入统一工具协议；
- 参与多 Agent 协作与任务拆解，支持父 Agent 委派、子 Agent 独立历史、结果回传，以及并行子任务的启动、等待、取消和清理；
- 参与记忆与项目隔离能力建设，将会话历史、FAISS 长期记忆、项目知识、工作区、指令、变量、密钥、MCP 和 Skills 按项目组织；
- 参与扩展与恢复能力建设，通过扩展钩子、Plugin、Skills、MCP、日志和 Time Travel 快照降低新业务工具的接入成本，并保留历史检查与回滚能力；
- 补充中文文档体系和 Agent Profile/Prompt 说明，沉淀安装、使用、架构、Browser、Desktop、Memory、Projects、MCP 等模块的中文资料。

## 系统架构与核心流程

### 总体分层

```text
Web UI / HTTP API / WebSocket
              ↓
      AgentContext 会话运行时
              ↓
  Agent Loop：Prompt → LLM → Action
              ↓
本地工具 / Plugin工具 / MCP工具 / 子Agent
              ↓
 Browser / Desktop / Shell / File / Document / Knowledge
              ↓
工具结果写入History → 再次组装上下文 → 下一轮决策
              ↓
 response工具或普通最终回答结束本轮任务
```

平台由 Flask 提供 HTTP/API 服务，WebSocket 用于推送消息、工具进度、状态快照和 Canvas 变化。`AgentContext` 管理一个聊天的运行状态，`Agent` 管理具体的推理与工具执行循环，`History` 保存消息和工具结果。工具既可以来自本地 `tools/` 与 Plugin，也可以来自 MCP Server。

### Agent执行闭环

```text
接收 UserMessage
→ 写入 History
→ 执行 monologue_start 扩展
→ 组装 System Prompt、Protocol、History、Extras
→ 调用主模型并流式输出 reasoning/response
→ 解析原生 function call 或 JSON 工具请求
→ 查找 MCP Tool 或本地 Tool
→ before_execution / execute / after_execution
→ 工具结果写回 History
→ 继续下一轮模型决策
→ response.break_loop=true 或模型直接给出最终回答
```

循环内会处理暂停、用户中途干预、重复回复、工具格式错误和异常。用户在工具执行中追加消息时，系统会保存当前工具进度，把干预消息写入历史，再让 Agent 基于新信息继续处理。

### Prompt与上下文组装

每轮 Prompt 由四类信息构成：

1. **System**：角色、行为约束、工具协议、Project 状态等；
2. **Protocol**：项目指令、已加载 Skill 等需要稳定保留的信息；
3. **History**：用户消息、模型回复和工具结果；
4. **Extras**：记忆召回、当前文件树、运行中的并行任务、Desktop 状态等临时信息。

扩展点可以在 Prompt 组装前后增删内容。系统会记录最终上下文文本和近似 Token 数，用于上下文窗口展示与压缩判断。

## 核心模块

### 1. 多轮会话与上下文管理

- `AgentContext` 保存聊天 ID、任务、日志、暂停状态、活动 Agent、项目和输出数据；
- `History` 把记录分成当前 Topic、历史 Topic 和 Bulk，兼顾最近细节与较早摘要；
- 上下文超过模型历史预算时，先压缩超长消息，再摘要 Topic，之后合并 Bulk；
- 聊天状态序列化到本地，重新加载后可恢复 Agent、History、日志和项目绑定；
- WebSocket 将状态变化推送给前端，HTTP Poll 保留兼容入口。

这里要区分“短期会话历史”和“长期记忆”：前者保证当前聊天连贯，后者通过 Embedding 召回跨聊天信息。

### 2. 工具调用与统一执行协议

所有工具继承 `helpers.tool.Tool`，统一实现：

- `before_execution()`：初始化日志并展示参数；
- `execute()`：执行实际动作，返回 `Response`；
- `after_execution()`：清洗结果、写回 History 并更新日志；
- `Response.break_loop`：决定结束 Agent Loop 还是继续下一轮。

模型调用兼容两种路径：支持原生 function calling 的模型可以直接返回结构化调用；其他模型可以按约定输出 JSON 工具请求。工具查找优先检查项目对应的 MCP 配置，再从 Agent Profile、Project、Plugin 和内置目录加载本地工具。

### 3. 多环境工具执行

| 能力 | 当前实现 | 关键位置 |
| --- | --- | --- |
| 浏览器自动化 | Playwright 驱动页面打开、读取、点击、输入、截图；按聊天维护 Browser Runtime | `plugins/_browser/` |
| Linux桌面 | Docker 内 XFCE/Xpra 桌面，会话状态、窗口信息和截图可进入上下文 | `plugins/_desktop/` |
| 代码执行 | 本地或 SSH 交互式 Shell，支持 TTY、超时、持续输出和后续输入 | `plugins/_code_execution/` |
| 文件编辑 | 读取、写入和补丁更新，并检查读后写和文件状态 | `plugins/_text_editor/` |
| 文档查询 | 解析本地文件或 URL，按目标问题查询 PDF、HTML、图片和文本 | `plugins/_document_query/` |
| 知识与记忆 | FAISS 相似度检索项目知识、记忆片段和历史解决方案 | `plugins/_memory/` |

浏览器、桌面和工作区文件不是三套互不相关的能力。它们共享聊天上下文、日志、项目目录和前端 Canvas，因此 Agent 可以先查网页，再生成文件，最后通过桌面应用检查结果。

### 4. 多Agent协作与任务拆解

串行委派通过 `call_subordinate` 完成：

```text
主Agent识别可拆分任务
→ 创建或复用子Agent
→ 为子Agent写入子任务消息
→ 子Agent在自己的History中执行Agent Loop
→ 子Agent返回结果并封存当前Topic
→ 结果作为工具结果回填主Agent
→ 主Agent综合结果继续执行
```

父子 Agent 拥有不同 History，避免子任务中间过程全部占用主 Agent 的上下文。子 Agent 可以选择 Developer、Researcher 等 Profile。当前实现还提供并行任务管理：为子 Agent 或直接工具调用创建 job，支持 `start`、`await`、`cancel`，并在完成后清理工作上下文。

并行不是越多越好。依赖同一浏览器、同一交互式终端或有先后依赖的任务仍应串行；独立检索、代码检查和资料整理更适合并行。

### 5. 长期记忆与知识召回

长期记忆使用 Embedding + FAISS，并把数据分成：

- `main`：长期保留的稳定信息；
- `fragments`：从对话中提取的片段；
- `solutions`：已解决问题的过程或方案；
- imported knowledge：从 TXT、PDF、CSV、HTML、JSON、Markdown 导入的项目知识。

每隔一定轮次，系统根据当前消息和历史生成检索 query，分别召回普通记忆和 solutions，可再通过模型做相关性过滤，然后把结果放入本轮 Extras。Embedding 模型变化时会重建索引；FAISS 文件带 SHA-256 校验，发现索引哈希不一致时重建。

该机制提高的是“找回相关信息”的概率，不等于模型拥有绝对可靠的永久记忆。陈旧记忆、错误摘要和不合理阈值仍会污染当前决策，需要提供查看、编辑、删除和重建入口。

### 6. Project隔离

每个 Project 位于独立工作区，并在 `.a0proj/` 下维护元数据。可隔离或配置：

- 项目描述与主指令；
- `AGENTS.md` 和附加 instruction 文件；
- 项目文件与 Git 仓库；
- 项目长期记忆和知识目录；
- variables 与 secrets；
- Skills、MCP Server 和子 Agent 开关；
- 模型 Preset 与 Plugin 配置。

激活 Project 后，项目指令被放入 Protocol，文件树放入 Extras，项目路径成为工具工作目录。记忆插件默认把索引写入项目自己的 `.a0proj/memory`，避免不同客户或任务的长期记忆互相召回。

### 7. Skills、Plugin与MCP扩展

- **Skill**：Markdown 形式的任务方法和资源，先发现元数据，再按需加载正文，适合沉淀可复用工作流；
- **Plugin**：可以组合 Python 扩展、工具、Prompt、API 和 Web UI，适合完整能力包；
- **MCP**：接入 stdio 或远程 HTTP MCP Server，把外部工具统一映射为 Agent Tool；
- **Agent Profile**：覆盖角色元数据、Prompt、工具和扩展，适合 Developer、Researcher 等不同工作方式；
- **A2A**：用于与外部 Agent 通信，补充平台内部父子 Agent 协作。

平台在 `Agent.monologue()`、Prompt 组装、模型调用、工具执行、消息写入和 WebSocket 事件等位置暴露扩展点，新能力可以通过目录约定和钩子接入，而不必把逻辑都写入 Agent 主循环。

### 8. 可观测性与恢复

- 每次模型输出、工具调用、参数、进度、结果和异常都会写入上下文日志；
- WebSocket 状态同步让前端能实时展示 reasoning、response、工具进度、Browser 和 Desktop；
- 聊天持久化保存 History 与日志，支持加载、导出和继续会话；
- Chat Compaction 在压缩前保留备份，再把长历史压成结构化摘要；
- Time Travel 对 `/a0/usr` 下的工作区建立 Git 对象快照，支持历史列表、diff、preview、travel 和 revert；
- 文本编辑、代码执行和工作区文件变化后可触发快照，回滚前自动建立保护快照。

Time Travel 保护的是 Agent 管理的工作区文件，不等同于数据库事务、容器镜像回滚或完整灾备。

## 关键难点与解决思路

### 难点一：如何让模型真正形成执行闭环

只解析一次工具调用不够。工具结果必须作为新消息回填 History，并再次调用模型，由模型判断是否继续、换工具还是结束。项目把这个过程放入 `monologue()` 的内层循环，并用 `Response.break_loop` 统一控制结束条件。

### 难点二：上下文增长导致性能和稳定性下降

解决方式不是简单删除旧消息，而是分层处理：保留当前 Topic 细节，对历史 Topic 做摘要，再把更早内容合并为 Bulk；长期稳定信息进入向量记忆，需要时再召回。子 Agent 也通过独立 History 隔离中间过程。

### 难点三：不同工具的生命周期和返回格式不一致

通过 `Tool` 基类统一执行前、执行中、执行后的行为，使用 `Response` 统一结果和是否结束循环；MCP 工具也适配成同样的 Tool 形态。这样日志、历史回填、错误处理和前端展示不依赖具体工具。

### 难点四：网页、桌面、Shell等有状态工具如何与聊天绑定

运行时按 `context_id` 管理，Project 提供工作目录，状态通过 Extras 和 WebSocket 回传。重置或删除聊天时清理 Browser 等运行时，避免不同会话复用错误状态。

### 难点五：扩展能力增加后如何避免主循环膨胀

在 Agent、模型调用、Prompt、History、工具和 WebSocket 周围提供同步/异步扩展点；Plugin 再把 Hook、Tool、Prompt、API 和 UI 打包。主循环只保留稳定骨架，业务能力通过扩展装配。

- 源码存在完整 Agent Loop、工具执行协议、上下文历史和持久化实现；
- Browser、Desktop、代码执行、文本编辑、文档查询、Memory、Skills、MCP、多 Agent 和 Time Travel 均有独立模块及接入点；
- 个人仓库当前 HEAD 为 `7892c81`，可核验到本人提交的中文文档体系和 Agent Profile/Prompt 说明；
- 本次仅做源码静态核验，没有补写并发量、成功率、延迟、Token 成本或业务效率提升比例。

## 项目不足与后续改进

- 本地 FAISS 更适合单实例，团队级部署需要评估持久化向量数据库、并发写入和数据迁移；
- 多 Agent 的委派质量仍依赖主 Agent 拆解能力，需要任务评估集和超时、Token、并发预算；
- 工具结果可能很长，除了历史压缩，还需要结果裁剪、结构化摘要和 Artifact 引用；
- Browser、Desktop、Shell 和 MCP 的权限不同，需要更细粒度的工具白名单、参数校验、审批和审计；
- Project 隔离主要是应用层目录与配置隔离，生产环境还要结合租户认证、文件权限、容器和网络策略；
- 当前缺少基于真实企业任务的成功率、平均步骤数、工具失败率、恢复率和成本数据；
- Time Travel 只覆盖 Agent 工作区文件，外部系统副作用需要幂等、补偿或人工确认机制。
