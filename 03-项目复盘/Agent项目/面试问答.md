# Agent项目面试问答

## 使用口径

- 项目性质：团队项目，我参与开发；
- 重点职责：Agent Loop、上下文与工具编排、多环境工具、多 Agent、Memory、Project 和扩展恢复；
- 只讲源码与真实经历能支撑的能力，不补写并发量、成功率、降本比例等数字；
- 回答遵循“为什么做—怎么设计—关键取舍—当前不足”的顺序。

## 项目介绍

### 请介绍一下这个项目

回答：

> 我参与开发的是一个面向企业复杂任务处理场景的通用 AI Agent 智能工作台。它不是只做问答，而是让模型在多轮循环中理解任务、选择工具、执行动作、读取结果并继续决策。平台接入了浏览器自动化、Linux 桌面、文件编辑、代码执行和文档查询，也支持父子 Agent 协作、FAISS 长期记忆、Project 隔离、Skills、Plugin、MCP 和工作区快照。我的主要工作是参与 Agent 运行闭环、上下文与工具编排、多环境工具接入、多 Agent 协作、记忆与项目隔离，以及扩展和恢复机制建设。

### 这个项目解决的核心问题是什么

回答：

> 核心问题是把大模型从一次性文本生成器变成可以在真实环境中持续完成任务的执行系统。普通聊天在遇到网页操作、文件处理、代码运行和跨轮次任务时缺少状态、工具和反馈闭环。我们通过 Agent Loop 管理“模型决策—工具执行—结果回填—再次决策”，再用 History、Memory、Project 和子 Agent 解决长任务中的上下文与协作问题。

### 你的具体职责是什么

回答：

> 我主要参与六块：第一是 Agent Loop 和 `AgentContext`，打通消息、Prompt、模型、工具和结果回填；第二是浏览器、桌面、文件、代码和文档工具的统一接入；第三是父子 Agent 委派和并行子任务；第四是会话历史、向量记忆和项目隔离；第五是 Skills、Plugin、MCP 与 Time Travel 扩展恢复；第六是中文文档体系和 Agent Profile/Prompt 说明。介绍时我会把团队整体能力和我实际参与的模块分开讲。

## Agent Loop与上下文

### Agent Loop是怎么工作的

回答：

> 用户消息先写入 History。每一轮会组装 System、Protocol、History 和 Extras，调用主模型；如果模型返回 function call 或 JSON 工具请求，就查找 MCP 工具或本地工具，依次执行 before、execute、after，把结果写回 History，再进入下一轮。模型直接返回最终回答，或者某个工具返回 `break_loop=true` 时结束。循环中还会处理暂停、用户干预、流式输出、重复回复和工具格式错误。

### 为什么要把Protocol、History和Extras分开

回答：

> 三者的生命周期不同。Protocol 放项目指令、已加载 Skill 等需要跨轮稳定存在的信息；History 是对话与工具结果；Extras 是记忆召回、文件树、Desktop 状态、并行任务等本轮动态上下文。分开后，扩展可以只更新对应区域，也方便控制哪些信息持久保留、哪些每轮重算。

### 如何处理用户在Agent执行过程中的新消息

回答：

> `AgentContext.communicate()` 会判断当前任务是否仍在运行。运行中就把消息作为 intervention 交给当前 Agent，并可以向上广播。Agent 在模型流式输出和工具执行的关键节点检查 intervention；如果收到新消息，会先保存工具进度，再把新消息写入 History，终止当前决策路径并基于新上下文继续。

### 如何防止上下文无限增长

回答：

> History 分成当前 Topic、历史 Topics 和 Bulks。超限后先压缩异常长消息，再摘要当前或历史 Topic，最后合并更早的 Bulk。历史预算由模型上下文长度乘 `ctx_history` 得到。长期稳定信息不一直塞在 History 里，而是进入向量记忆，需要时再召回。子 Agent 也有自己的 History，可以隔离子任务过程。

### History压缩会不会丢信息

回答：

> 会有信息损失，所以它是有取舍的。当前策略优先保留最近消息和任务状态，较早内容做摘要，嵌入数据超限时也会移除。为了降低风险，Chat Compaction 会在压缩前保存备份。进一步可以加入结构化任务状态、必须保留字段、摘要一致性检查和压缩前后问答评估，而不是只依赖自由文本摘要。

## 工具调用

### 工具系统怎么设计

回答：

> 所有本地工具继承统一 `Tool` 基类，实现 `before_execution`、`execute` 和 `after_execution`，统一日志、参数展示、进度、History 回填和结束控制。工具返回统一 `Response(message, break_loop, additional)`。MCP Tool 也适配成同一形态，因此 Agent Loop 不需要关心底层是 Python 工具、Plugin 还是远程 MCP Server。

### 模型不支持Function Calling怎么办

回答：

> 平台保留两条解析路径。支持原生 function calling 或 Responses API 的模型直接返回结构化调用；其他模型按照 Prompt 约定输出 JSON，系统做容错解析和结构校验。解析失败时把格式问题写入 History，让模型下一轮修正。这样兼容性更好，但 JSON 协议比原生 function calling 更依赖模型遵循能力。

### 工具执行结果为什么必须写回History

回答：

> 工具执行只是获得环境反馈，任务是否完成仍要由 Agent 基于结果判断。如果结果不回填，模型不知道网页是否打开、命令是否成功、文件写到哪里，也就不能纠错或选择下一步。写回后才形成真正的 observe—reason—act 闭环。

### 如何处理工具输出过长

回答：

> 当前 History 会压缩超长消息，部分工具也可以把大结果保存成文件并只返回引用。更完整的方案是按工具类型做结构化裁剪：Shell 保留错误和尾部输出，文档查询返回相关段落，Browser 返回目标 DOM 与截图引用，大型 Artifact 写文件。核心原则是保留下一步决策需要的信息，而不是把原始输出全部塞进上下文。

### MCP工具和本地工具冲突怎么办

回答：

> 当前执行路径会先按项目对应的 MCP 配置查找工具，再回退到本地工具加载。工程上应对工具名做 namespace 规范，例如 `server.tool`，并在配置阶段检查重复名。Project 级 MCP 配置还要与全局配置合并，避免不同项目使用错误服务。

## 多环境执行

### 浏览器自动化是怎么接入的

回答：

> Browser 作为 Plugin 提供统一工具和按 `context_id` 管理的 Playwright Runtime。Agent 可以打开页面、读取内容、点击、输入、上传和截图，Web UI 通过 WebSocket 展示实时 Browser 状态。聊天重置或删除时会清理对应 Runtime，避免会话状态串扰。

### Browser和Linux Desktop有什么区别

回答：

> Browser 面向网页 DOM，操作目标结构化、可定位，优先用于网页任务；Desktop 面向完整 Linux GUI，可以操作没有网页 API 的桌面软件。Desktop 会采集窗口、指针和截图等状态并注入上下文。二者都展示在 Canvas，但执行对象和定位方式不同。

### 代码执行如何支持交互式命令

回答：

> 代码执行模块维护本地或 SSH 的交互式 Session，底层使用 TTY/PTY 读取持续输出。系统区分首次输出、两次输出间隔、最大执行时长和对话提示超时；命令进入交互等待时，Agent 可以通过 input 工具继续发送键盘内容，而不是每次都启动新进程。

### 文件编辑为什么要强调先读后写

回答：

> 直接覆盖容易丢掉用户或其他工具刚做的修改。Text Editor 会记录读取状态和文件上下文，补丁执行时检查是否读过、内容是否已经变化。配合 Time Travel，文件写入或补丁后生成快照，可以检查 diff 并在必要时回滚。

## 多Agent协作

### 父子Agent如何协作

回答：

> 主 Agent 通过 `call_subordinate` 传入明确子任务和可选 Profile。子 Agent 有独立 History，在同一聊天上下文中执行自己的 Agent Loop，完成后把结果作为工具结果返回主 Agent，并封存当前 Topic。这样主 Agent 只接收结论，不必承担所有中间推理和工具输出。

### 为什么不用一个Agent完成所有任务

回答：

> 长任务里，研究、编码、测试等子任务会产生大量过程信息，一个 Agent 容易上下文过载，也不利于角色专注。子 Agent 可以用不同 Profile 和独立 History处理局部问题。但子 Agent 会增加模型调用、协调和错误传播成本，所以只在任务可明确拆分、结果可验证时使用。

### 串行委派和并行任务怎么选择

回答：

> 有数据依赖、共享交互式 Browser/Shell 或需要前一步结果的任务用串行。相互独立的资料检索、文件检查和候选方案比较可以并行。并行任务支持 start、await、cancel 和清理，但仍要设置并发数、超时和 Token 预算，避免并行放大成本。

### 如何防止子Agent无限递归

回答：

> 当前工具层会阻止并行 worker 再递归发起并行调用，Profile 和任务层也应限制委派深度。生产设计还需要统一的最大层级、最大子任务数、总 Token、总耗时和取消传播，并把这些预算放在 AgentContext 或任务调度器中集中管理。

### 子Agent失败怎么办

回答：

> 子 Agent 结果应带完成状态、错误和可验证产物，主 Agent 决定重试、缩小任务或回退自己执行。并行任务要支持 cancel 和上下文清理。对有副作用的任务，不能只重跑整个子任务，还要检查已经产生的文件或外部操作，必要时通过快照或补偿恢复。

## Memory与Project

### 短期记忆和长期记忆有什么区别

回答：

> 短期记忆就是当前聊天 History，按时间顺序保留消息、工具结果和摘要；长期记忆使用 Embedding + FAISS 保存跨聊天的稳定信息、片段和历史解决方案。每轮按当前问题检索相关记忆并注入 Extras。短期记忆强调会话连续性，长期记忆强调按需召回。

### 长期记忆的召回流程是什么

回答：

> 系统根据当前用户消息和部分历史生成检索 query，分别搜索普通 memory/fragments 和 solutions，使用相似度阈值和数量上限筛选；可选地再让 utility model 做相关性过滤，最后把保留内容放进 Prompt。查询准备和后过滤提高相关性，但会增加延迟和 Token 成本。

### 为什么选FAISS

回答：

> 这个工作台优先支持本地和单实例部署，FAISS 集成简单、检索快，适合先把长期记忆链路做完整。代价是多实例并发、在线迁移、权限过滤和运维能力有限。如果要做企业级多租户，需要评估 pgvector、Milvus、Qdrant 或其他服务化向量库。

### 如何避免错误记忆污染后续任务

回答：

> 记忆需要可查看、编辑、删除和重建，不能把每次对话都当成事实永久保存。写入前可做质量判断和相似记忆合并，召回后再做相关性过滤；Project 级隔离避免跨业务串扰。还要保留来源、时间和类型，遇到行为异常时优先审查 Memory。

### Project隔离了什么

回答：

> Project 提供独立工作目录和 `.a0proj` 元数据，可配置描述、指令、AGENTS.md、知识、长期记忆、variables、secrets、Skills、MCP、子 Agent 和模型 Preset。激活后项目指令进入 Protocol，文件树进入 Extras，工具在项目路径工作，Memory 默认写入该项目自己的索引。

### Project隔离是不是安全沙箱

回答：

> 不是同一个概念。Project 首先是应用层的上下文和目录隔离，避免文件、记忆和配置混用。真正的安全边界还依赖账号权限、文件系统权限、容器、网络策略、工具白名单和密钥管理。特别是连接宿主机或远程 MCP 后，权限边界会扩大。

## Skills、Plugin与MCP

### Skills和Tools有什么区别

回答：

> Tool 是可执行能力，定义参数并返回结果；Skill 是任务方法，告诉 Agent 在某类任务中如何组合工具、遵循什么步骤和读取哪些资源。Skill 可以按需加载，减少所有说明常驻上下文。一个 Skill 通常会调用多个 Tool。

### Plugin和Extension有什么区别

回答：

> Extension 是某个生命周期钩子的具体实现，例如在 Prompt 组装后注入 Memory；Plugin 是能力包，可以同时包含 Extensions、Tools、Prompts、API、配置和 Web UI。Extension 是机制，Plugin 是交付与装配单位。

### 为什么需要MCP

回答：

> 如果每个外部服务都写一套私有适配器，工具 Schema、连接和生命周期会重复。MCP 用统一协议描述工具和调用结果，平台把 stdio 或远程 HTTP Server 映射成统一 Tool。这样业务系统可以独立部署，Project 只需配置需要的 Server。

### 如何避免所有Skill都占用上下文

回答：

> 系统先扫描 Skill 元数据并把名称、描述等简短信息暴露给 Agent；匹配任务后再通过 `skills_tool` 加载完整 `SKILL.md`。已加载 Skill 放入稳定 Protocol，并在历史压缩后重新附着。这个过程属于渐进式披露。

## 可观测性、恢复与安全

### 如何观察一次Agent任务发生了什么

回答：

> `Log` 记录模型输出、工具名称、参数、进度、结果和异常，WebSocket 持续把日志与状态快照推送给前端。通过 Context ID 可以串起一轮会话中的模型和工具行为。进一步生产化时，我会补 trace_id、模型耗时、Token、工具耗时、重试次数和任务结果标签。

### Time Travel是怎么实现的

回答：

> 它把 Agent 管理的 `/a0/usr` 工作区作为 Git 对象仓库维护。文件写入、补丁、代码执行或 Watchdog 变化可以触发 snapshot；用户可以查看 history、diff 和 preview，再执行 travel 或 revert。回滚前会自动保存当前状态，降低误操作风险。

### Time Travel和Git有什么区别

回答：

> 底层复用了 Git 对象和 diff 能力，但产品目标是给 Agent 工作区提供自动快照和可视化回滚，不要求用户手工提交。它也不替代业务仓库的规范 Git 流程，更不覆盖数据库和外部系统副作用。

### 工具权限如何控制

回答：

> 当前主要通过 Docker 环境、Project 配置、Secrets 管理、MCP 配置、工具加载范围和输入校验控制。生产环境还要增加按用户与项目的工具白名单、危险动作确认、出网策略、文件路径限制、审计日志和凭据最小权限。连接宿主机 Browser、Shell 或远程服务时要单独评估权限。

## 评估与优化

### 如何评估Agent系统

回答：

> 我会分五层：任务层看端到端成功率和结果正确性；规划层看步骤数、无效循环和子任务拆解质量；工具层看调用成功率、参数错误率、重试和耗时；上下文层看关键信息保留率、召回准确率和压缩损失；系统层看P50/P95延迟、Token成本、并发、取消和恢复率。不同任务类型要分别统计，不能只看一个总成功率。

### 项目当前最大的不足是什么

回答：

> 第一，当前缺少一套真实企业任务评估集和稳定的质量、延迟、成本数据；第二，FAISS和应用层Project隔离更偏单实例，需要进一步做多租户和服务化；第三，Browser、Desktop、Shell、MCP的权限和副作用需要更细的策略；第四，多 Agent 还需要统一预算和结果校验，避免成本增加但质量没有提升。

### 如果让你继续优化，你会先做什么

回答：

> 我会先建任务评估集和可观测指标，因为没有基线就无法判断优化是否有效。随后做三件事：给 Agent 和子 Agent 增加总步数、Token、耗时和并发预算；对不同工具做结构化结果裁剪；补项目级认证授权与高风险工具审批。最后再根据评估结果调整 Memory、Prompt 和并行策略。
