# Agent 为什么会执行失败？超时、重试和终止条件应该怎么设计？

> [!info] 发布归档
> 公众号页面、作者和发布时间已核验。本地保留文章入口、内容提要与知识库关联；完整正文、代码排版和图片以[公众号原文](https://mp.weixin.qq.com/s/y0aXlUwZHbDNlE7U7H2tFw)为准。

Agent 系列第八篇。前七篇已经把 Agent 的基本结构、执行循环、规划、工具、Memory 和 State 串了起来。这一篇开始处理 Demo 跑通后的工程问题：模型会选错工具，接口会超时，循环可能失控，State 也可能丢失或被并发修改。

## 内容提要

文章把失败来源分为模型判断错误、工具执行失败、Agent Loop 失控和 State 错误。模型输出只能作为调用建议，程序仍需校验工具、参数、权限和业务规则，并保留错误原本的业务含义，避免把数据不存在、权限不足和临时网络错误都包装成同一种异常。

超时需要分层设置：模型调用、工具调用、单轮执行和整体任务分别有上限，并共享任务截止时间。调用方超时不代表下游操作没有成功；只读工具可以有限重试，写操作应先查询执行状态，高风险操作在结果不明时转人工处理。

重试部分强调错误分类、次数与时间边界、任务总预算、指数退避与随机抖动，并要求把每次失败和重试写入 State。写操作使用稳定幂等键。终止条件由程序根据任务状态、预算、执行轨迹和可计算的进展强制执行；模型声称完成后，程序还要检查真实成功条件。

任务恢复依赖完整 State：失败步骤、结构化错误、重试次数、调用轨迹、幂等键、任务版本和恢复位置都要保留。恢复前需要重新检查结果有效期、副作用状态、并发接管情况和剩余预算，同时把内部错误详情与面向用户的提示分开。
