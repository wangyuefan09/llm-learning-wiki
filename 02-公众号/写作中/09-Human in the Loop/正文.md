# Agent 什么时候必须停下来等人确认？一篇讲清 Human in the Loop

Agent 系列第九篇。

State 保存任务现场，超时、重试和终止条件负责收住异常执行。任务没有报错时，也有一些步骤不能自动往下走：工具能够正常调用，但这一步不该由 Agent 自己决定。

比如，用户让 Agent 分析一次线上故障，整理受影响客户，并生成通知。Agent 查完日志，写好了说明，也拿到了客户名单。下一步是批量发送。

技术上没有障碍。也正因为如此，这一步容易出问题。

如果 Agent 把通知发错了人，或者把还没确认的故障原因写进正文，接口返回 `200` 也没有意义。程序应该在发送前暂停，把动作交给有权限的人确认。这类执行中的人工检查，通常被称为 Human in the Loop，简称 HITL。

## 人应该进入执行链路，而不是留在提示词里

最简单的做法是在 System Prompt 中加一句：

```text
执行高风险操作前，必须先询问用户。
```

这句话有用，但它只能影响模型的选择。模型可能没有识别出风险，也可能在长任务中漏掉约束。更麻烦的是，外部网页、文档或工具结果里还可能混入干扰指令。

审批规则应该放在工具执行入口。模型提出动作后，运行时先校验工具名、参数、权限和业务状态，再判断是否要暂停。没有审批结果，工具执行器就不接收这次调用。

```text
模型提出 Tool Call
        ↓
参数与权限校验
        ↓
风险策略判断
   ┌────┴────┐
低风险      需要审批
   ↓           ↓
执行工具    保存动作与任务现场
               ↓
        WAITING_FOR_CONFIRMATION
```

HITL 和普通用户消息也不一样。用户在 Agent 运行时补充要求，程序把新消息写入 History，再从新上下文继续推理。审批则是一道明确的执行门：当前动作在 State 中等待，只有结构化的批准结果才能放行。

## 由运行时判断哪些动作要停

让模型给自己的动作打风险标签，看起来省事，实际会把审批边界交回模型。风险策略更适合由程序维护，判断依据包括副作用、影响范围、可撤销性、数据敏感度和当前用户权限。

我会先按四档处理：

| 类型 | 示例 | 处理方式 |
| --- | --- | --- |
| 只读操作 | 查询日志、读取配置 | 自动执行并记录 |
| 低影响写入 | 保存本地草稿、生成临时文件 | 执行后记录，必要时支持回滚 |
| 高影响操作 | 对外发送、批量修改、发布内容 | 执行前审批 |
| 无权限操作 | 访问未授权数据、调用未开放工具 | 直接拒绝 |

同一个工具也可能落在不同档位。查询一条公开记录与导出整库数据，调用的也许是同一个检索工具，影响范围却完全不同。策略判断不能只看工具名，还要检查参数、目标数量、调用者身份和任务上下文。

我更倾向于把这套规则放在统一 Tool Gateway 中。这样，本地工具、MCP Tool 和业务 API 走同一个检查入口。否则每个工具自己写一套审批逻辑，时间久了很容易漏掉一条路径。

## 用户批准的究竟是哪次操作

回到故障通知的例子。

Agent 第一次准备发送时，目标是 126 位客户，正文版本是 `NOTICE_V3`。等待确认期间，Agent 又收到一条补充信息，正文改成了 `NOTICE_V4`，客户名单也增加到 143 人。

此时，用户先前对 126 人和 `NOTICE_V3` 的批准不能继续使用。确认按钮批准的应该是一份固定的动作快照，而不是一句宽泛的「同意发送」。

一条审批记录至少要保存这些内容：

```json
{
  "approval_id": "APPROVAL_ID",
  "task_id": "TASK_ID",
  "task_version": 12,
  "status": "WAITING_FOR_CONFIRMATION",
  "tool": "send_incident_notice",
  "target_summary": "CUSTOMER_SET_VERSION",
  "content_artifact": "NOTICE_ARTIFACT_ID",
  "arguments_digest": "ACTION_DIGEST",
  "risk_reasons": ["external_write", "batch_operation"],
  "expires_at": "EXPIRES_AT",
  "idempotency_key": "IDEMPOTENCY_KEY"
}
```

`arguments_digest` 由工具名、规范化参数、目标版本和内容版本计算。批准后，其中任何一项发生变化，系统都重新发起审批。

审批界面也要把这些信息说清楚：执行什么动作，影响哪些对象，预计影响多少条数据，能否撤销，以及批准在什么时候过期。界面只显示必要摘要，凭据和敏感参数仍保存在服务端。

## 等待确认是一种任务状态

审批可能持续几分钟，也可能跨过一次服务重启。只在进程内保存一个布尔值，页面刷新后就找不到原来的任务了。

更稳妥的状态流转是：

```text
RUNNING
   ↓ 命中审批策略
WAITING_FOR_CONFIRMATION
   ├─ REJECTED
   ├─ EXPIRED
   ├─ CANCELLED
   └─ READY_TO_EXECUTE
              ↓
          EXECUTING
          ├─ SUCCEEDED
          └─ FAILED
```

进入 `WAITING_FOR_CONFIRMATION` 前，系统先保存 Checkpoint。除了待审批动作，还要记录已完成步骤、工具结果引用、任务版本、剩余预算和恢复位置。用户拒绝时，Agent 根据拒绝原因修改计划；审批过期则终止这次动作，不能默认当作同意。

这里有个容易混淆的细节：`APPROVED` 只表示审批决定已经产生，不等于工具已经执行成功。把审批结果和执行结果拆成不同状态，日志排查时会省很多麻烦。

## 用户点了同意，程序还要再检查一遍

等待期间，权限、资源状态和任务内容都可能变化。恢复执行时，程序应重新加载 State，并完成以下校验：

1. 审批记录仍然有效；
2. 审批人有权批准这类动作；
3. 当前任务版本与审批记录一致；
4. 重新计算的 `ACTION_DIGEST` 没有变化；
5. 目标资源仍处于允许操作的状态；
6. 任务预算和凭据仍然可用。

随后，执行器以原子方式把状态从 `READY_TO_EXECUTE` 改为 `EXECUTING`。两个页面同时点击确认时，只允许一个请求拿到执行权。工具调用沿用创建审批时生成的幂等键，避免页面重试、消息重复投递或服务重启造成二次发送。

```python
state = load_task(TASK_ID)
approval = load_approval(APPROVAL_ID)

validate_approval(
    approval,
    expected_task_version=state.version,
    expected_digest=digest(state.pending_action),
    now=now(),
)

recheck_permission(approval.approved_by, state.pending_action)
recheck_resource_state(state.pending_action)

claimed = compare_and_set_task_status(
    TASK_ID,
    expected="READY_TO_EXECUTE",
    new="EXECUTING",
)
if not claimed:
    return "ALREADY_CLAIMED"

execute_once(
    state.pending_action,
    idempotency_key=approval.idempotency_key,
)
```

第八篇提到过一种棘手情况：调用方超时了，下游操作却可能已经成功。审批流程遇到这种任务时，不能弹出一个「是否重试」就再次执行。系统应该先查询原操作状态，确认没有产生副作用，再决定恢复、补偿或交给人工处理。

## 确认框太多，用户就会一路点下去

如果读取文件、生成草稿、查询日志都要确认，HITL 很快会变成点击任务。用户没有时间逐项核对，最后只会机械地按「同意」。

审批应靠近真实副作用：只读操作自动运行，外部写入先生成 Dry Run，高影响动作展示差异后再确认。多个目标和参数都已确定的动作可以合并审批；只要范围或内容发生变化，就重新生成审批记录。

还要区分「需要审批」与「不允许执行」。用户没有某项权限时，系统直接拒绝调用。弹出确认框不会凭空增加权限。

判断审批设计是否可用，可以记录等待时长、审批过期率、无效审批比例、恢复成功率和重复副作用次数。测试时主动修改待执行参数、重复点击批准、重启服务、让审批过期，再安排两个审批人同时操作。状态机的问题通常会在这些场景里暴露出来。

## 放回当前项目来看

当前项目源码能够核验的是 `intervention`：Agent 在模型流式输出和工具执行前后检查用户的新消息，保存已有进度，再用更新后的上下文进入下一轮。这个机制解决了长任务中的用户打断。

完整的 HITL 还要增加风险策略、审批记录、动作摘要、过期处理和恢复校验。按我目前对项目的理解，这部分适合放在统一工具生命周期和任务 State 之间：模型继续负责提出动作，运行时负责决定动作能否执行。

整理这部分时，我最在意的已经不是界面上的确认按钮，而是按钮背后的状态：用户批准了哪一步，等待期间什么发生了变化，恢复时怎样保证只执行一次。少了这些记录，那个按钮只是让人心里踏实一点。
