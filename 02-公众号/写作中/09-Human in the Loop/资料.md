# 资料

## 写作目标

回答一个问题：Agent 准备执行有外部副作用的操作时，系统依据什么暂停任务，怎样记录审批信息，并在用户确认后安全恢复执行？

## 与系列前文的衔接

- 第七篇 [[02-公众号/已发布/Agent系列/07-State/正文|Agent 的状态是什么？为什么多步骤任务需要 State]] 讨论了 `WAITING_FOR_CONFIRMATION`、Checkpoint 与任务恢复。
- 第八篇 [[02-公众号/已发布/Agent系列/08-超时重试与终止条件/正文|Agent 为什么会执行失败？超时、重试和终止条件应该怎么设计？]] 讨论了结果未知、高风险操作人工介入、幂等键和恢复前校验。
- 第九篇继续回答：任务并未失败，但下一步影响较大时，怎样把人工决定接入 Agent Loop。

## 贯穿案例

用户让 Agent 分析一次服务故障、生成说明，并通知受影响客户。日志查询、影响分析和草稿生成可以自动完成；批量发送通知会影响外部对象，需要在工具执行前暂停。

重点讨论两个变化：

1. 等待期间，通知正文被重新生成；
2. 受影响客户范围发生变化。

这两种变化都会使原审批失效，用来说明审批必须绑定具体动作快照，而不是绑定一句宽泛的「可以发送」。

## 内容边界

### 已有事实

- Agent Zero 当前实现会在模型流式回调、工具执行前后检查 `intervention`，接收用户的新消息并重新进入循环。来源：[[01-Agent基础与运行循环]]。
- 当前项目通过工具生命周期、Project 配置、输入校验和运行环境约束工具执行；项目复盘把高风险工具审批列为生产化补充项。来源：[[03-项目复盘/Agent项目/面试问答|Agent项目面试问答]]。
- State、Checkpoint、幂等键、任务版本和恢复位置已经在系列第七、八篇中解释。

### 外部资料中的通用机制

- OpenAI Agents SDK 的 Human-in-the-loop 文档介绍了工具审批、暂停运行和基于运行状态继续执行的机制。
- LangGraph 的 Interrupts 文档介绍了在节点中暂停、通过 Checkpointer 保存状态，并用 resume 值恢复执行的机制。
- 两份资料都说明了同一件事：人工确认要进入运行时和持久化状态，不能只依赖 Prompt 约束。

### 个人理解与设计方案

- 用运行时策略判断风险，不让模型自行决定是否跳过审批。
- 审批记录保存工具名、目标、参数摘要、动作摘要、任务版本和有效期。
- 用户批准后重新校验权限、资源版本和动作摘要，再使用幂等键执行。
- 当前仓库没有完整结构化审批状态机的实现证据，正文将这部分表述为生产化设计方案，不写成已落地功能。

## 文章结构

1. 故障通知案例：Agent 做到发送前停下。
2. Human in the Loop 在执行链路中的位置。
3. 用运行时策略判断哪些动作需要审批。
4. 审批绑定动作快照，避免「批准 A、执行 B」。
5. 用 State 和 Checkpoint 保存等待现场。
6. 用户批准后的重新校验、并发控制与幂等执行。
7. 控制审批数量，避免用户机械点击。
8. 说明当前项目事实与后续设计的边界。
