# 混合检索与结果融合

## 稠密、稀疏与混合检索

### 稠密向量检索

使用 Embedding 表示语义，适合召回措辞不同但含义相近的内容。

### 稀疏检索

使用词项及其权重表示文本。BM25 是常用算法，擅长故障码、型号、专有名词等精确词项。

### 混合检索

同时执行关键词与向量检索，再融合两路候选。它适合既有精确术语又有自然语言描述的知识库。

## 向量检索容易失效的场景

- chunk 太大导致主题混杂；
- chunk 太小导致证据不完整；
- query 太短、太模糊；
- 业务要求精确匹配故障码、型号或部件号；
- Embedding 模型不理解行业术语；
- 过滤条件在召回前排除了正确结果。

这些场景需要结合 BM25、元数据过滤、查询改写和重排处理。

## 项目当前检索链路

项目的 OpenSearch 查询链路是：

```text
用户查询
→ 生成 query embedding
→ BM25 检索 + HNSW ANN 检索
→ OpenSearch search pipeline 使用 RRF 融合
→ 返回 Top-K chunk
```

在 Agentic RAG 路径中，文档还会经过 LLM 相关性评分；如果全部候选都不相关，系统改写 query 后再次检索。

项目当前没有独立的 Cross-Encoder Reranker。LLM 文档评分节点属于结果过滤和路由，不应直接称为已接入 Reranker 模型。

## RRF

RRF（Reciprocal Rank Fusion）融合的是排名，不直接比较不同检索器的原始分数。

常见形式：

```text
RRF(d) = Σ 1 / (k + rank_i(d))
```

优势：

- 不要求 BM25 和向量分数处于同一尺度；
- 不需要先做复杂归一化；
- 对不同 query 类型通常比较稳健。

当前项目的 OpenSearch pipeline 使用 `rank_constant=60`。

## 加权分数融合

加权融合先归一化各检索器分数，再计算类似：

```text
score = 0.3 × bm25_score + 0.7 × vector_score
```

它允许明确表达业务偏好，但归一化方法和权重需要通过评估集调参。同一组权重未必同时适合精确故障码和自然语言问答。

当前项目源码只创建 RRF pipeline，没有保留可直接启用的加权融合 pipeline。加权融合属于可通过评估集实现和对比的备选方案。

## 判断Embedding问题还是chunk问题

更像 chunk 问题：

- 召回主题正确，但证据总缺少关键上下文；
- 命中块包含多个不相关主题；
- 同一答案被切散到相邻块。

更像 Embedding 问题：

- chunk 本身完整清楚，但同义表达召回不到；
- 行业术语和通用词的语义被混淆；
- 相关文本在向量空间中的排名持续偏低。

还要排除 query 改写、过滤条件、索引配置和融合策略问题，不能只凭单个样本下结论。

## 检索评估

建立带相关文档或相关 chunk 标注的问答集，至少覆盖：

- 同义改写问题；
- 精确术语和故障码；
- 真实用户口语；
- 多条件和长问题；
- 无答案问题。

常用指标：

- Recall@K：前 K 个结果是否覆盖相关证据；
- Precision@K：前 K 个结果中相关证据占比；
- MRR：第一个相关结果的排名；
- nDCG@K：考虑相关性等级和排序位置；
- 检索延迟与候选数量。

“Recall@5”不是“找回多少相关内容”的完整定义。它通常表示前 5 个结果召回的相关项占全部相关项的比例，具体计算口径应在评估方案中固定。
