# RAG基础概念与常见形态

## RAG是什么

RAG（Retrieval-Augmented Generation，检索增强生成）是一种把外部检索结果加入模型上下文，再让大语言模型生成回答的应用架构。

它不直接修改模型参数。系统先检索与问题相关的资料，再把问题、资料和回答要求一起交给模型。外部资料因此成为回答时的临时知识和证据。

RAG主要解决三类问题：

- 模型训练知识无法及时更新；
- 模型无法直接访问企业私有数据；
- 回答缺少可追溯的证据。

RAG只能降低幻觉风险，无法自动消除幻觉。检索错误、上下文噪声、提示词设计和生成模型本身都会影响最终答案。

## 基本流程

```text
文档加载与解析
→ 文本清洗和切分
→ Embedding
→ 向量与元数据入库
→ 用户查询向量化
→ 检索召回
→ 可选的融合、重排与过滤
→ 组装 Prompt
→ LLM 基于证据生成回答
```

### 离线索引阶段

1. 加载 PDF、DOCX、Markdown、网页等资料。
2. 解析正文、标题、表格和元数据。
3. 将文档切成适合检索的 chunk。
4. 使用 Embedding 模型将 chunk 转为向量。
5. 保存文本、向量、来源和权限等元数据。

### 在线问答阶段

1. 接收用户问题。
2. 将查询编码到与文档兼容的向量空间。
3. 通过向量、关键词或混合检索召回候选 chunk。
4. 对候选结果进行重排、过滤或上下文压缩。
5. 将保留的证据与原问题交给 LLM。
6. 返回答案和来源。

## 常见形态

RAG没有一个公认且互斥的“固定七种范式”。下面这些名称描述的是不同优化方向，同一个系统可以同时属于多类。

### Naive RAG

最小链路通常是“向量检索 + Prompt 拼接 + LLM 生成”。它适合验证方案，但容易受到查询表达、chunk 质量和召回噪声影响。

### Advanced RAG

在检索前后增加质量优化，例如：

- 查询改写与多查询扩展；
- 混合检索和元数据过滤；
- Reranker 重排；
- 上下文压缩、去重和证据过滤。

目标是提高有效证据的召回率和排序质量，而不是单纯增加返回数量。

### Modular RAG

把固定链路拆成可组合模块，例如 Query Router、Retriever、Memory、Reranker 和 Generator。系统可以按问题类型选择知识源、检索器和生成策略。

### Agentic RAG

由 Agent 决定是否检索、使用哪个工具、是否改写查询以及是否继续检索。与固定 RAG 链路相比，它增加了状态、路由和循环。

### Graph RAG

使用实体、关系、事件或社区等图结构组织知识，适合需要跨文档关系聚合和全局主题总结的问题。微软 GraphRAG 是其中一种具体实现，不能代表所有基于知识图谱的 RAG。

### Corrective RAG与Self-RAG

二者都关注检索和生成质量，但不是同一个方法：

- Corrective RAG 会评估检索结果，并在质量不足时纠正查询、替换来源或补充搜索；
- Self-RAG 把“是否检索、证据是否相关、回答是否受支持”等自我反思信号纳入生成过程。

### 多模态RAG

知识源扩展到图片、表格、音频或视频。难点包括内容表示、跨模态对齐、检索粒度以及如何把多模态证据组织进模型上下文。

## 一句话理解演进方向

RAG的演进不是一条严格的版本线，而是不断提升检索质量、模块可组合性、决策自主性和证据可靠性的过程。
