# 文档解析与结构化

## 文档解析的作用

文档解析负责把 PDF、DOCX、Markdown、TXT 等不同输入转换成统一结构，为清洗、切分、向量化和溯源提供稳定接口。

常见工具包括：

- PyMuPDF4LLM：把 PDF 转成适合 LLM 处理的 Markdown；
- Unstructured：处理多种文档格式并提取元素；
- LangChain TextLoader：加载纯文本；
- Firecrawl：抓取和清洗网页内容；
- Docling：解析 PDF、DOCX 等格式，支持布局、OCR 和表格结构识别。

不同版本和运行环境支持的格式、OCR 引擎与表格能力可能变化，实际选型需要用目标文档集测试。

## 项目为什么使用Docling

项目目标是将 PDF、DOCX、Markdown 和 TXT 转换为统一的 `DocumentContent`：

- PDF、DOCX 使用 Docling；
- Markdown、TXT 使用轻量文本解析器；
- `DocumentParserService` 根据文件扩展名路由。

源码位置：

- `src/services/document_parser/parser.py`
- `src/services/document_parser/pdf.py`
- `src/services/document_parser/docx.py`
- `src/services/document_parser/md.py`
- `src/services/document_parser/txt.py`

## 统一输出字段

项目中的 `DocumentContent` 包含：

- `sections`：标题、正文和层级组成的章节列表；
- `raw_text`：按阅读顺序整理的全文文本；
- `tables`：表格标题、二维行列、Markdown 和 HTML 表示；
- `figures`：图片信息，目前具体解析器返回空列表；
- `parser_used`：Docling 或轻量文本解析；
- `metadata`：来源格式、解析参数、表格数量和阅读顺序信息。

源码位置：`src/schemas/document_parser/models.py`。

## sections、raw_text和tables如何进入下游

当前索引链路优先把 `sections` 交给 section-aware `TextChunker`；没有有效 sections 时，使用 `raw_text` 做全文切分兜底。

`tables` 已经形成双链路：

1. 原始 rows、Markdown 和 HTML 按文档版本保存到 PostgreSQL 的 `document_tables`；
2. `TableChunker` 重复文档标题、表题和表头，把行列关系展开为语义文本，生成 `chunk_type=table` 的 OpenSearch 切片，并保存 `table_id`、`row_start` 和 `row_end`。

检索命中表格切片后，可以回查 ready 活动版本的原始表格结构。复杂合并单元格、跨页表格和 OCR 表格的准确率仍需真实样本验证。

## PDF解析流程

当前 PDF 解析包括：

1. 校验文件大小、PDF 文件头和页数；
2. 调用 Docling 进行版面分析；
3. 按配置启用 OCR 和表格结构识别；
4. 提取文本元素；
5. 优先使用文档树顺序，并在检测到双栏时结合坐标重排；
6. 构建 `raw_text`、`sections` 和 `tables`；
7. 返回统一的 `DocumentContent`。

相关配置包括：

- `do_ocr`；
- `do_table_structure`；
- `table_structure_mode`；
- `table_cell_matching`；
- `reading_order_postprocess_enabled`；
- `ocr_engine`；
- `force_full_page_ocr`。

## 解析质量评估

可以建立一批包含双栏、扫描页、跨页表格和复杂标题层级的样本文档，检查：

- 正文阅读顺序是否正确；
- 标题层级是否保留；
- OCR 字符错误率；
- 表格行列和合并单元格是否正确；
- sections 缺失率；
- raw_text fallback 比例；
- 空文档、异常文档和超限文档比例。
