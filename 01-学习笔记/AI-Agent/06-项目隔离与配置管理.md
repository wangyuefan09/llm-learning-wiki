# 项目隔离与配置管理

## 为什么需要Project

通用 Agent 同时处理多个客户、代码库或研究主题时，最常见的问题不是模型能力不足，而是上下文串扰：错误工作目录、旧项目记忆、同名密钥、错误 MCP Server 或不相关指令进入当前任务。

Project 的作用是把“Agent 正在哪个世界里工作”显式化。

## Project包含什么

项目当前实现可以组织：

- 标题、描述与主 Instructions；
- 根目录 `AGENTS.md` 与附加 instruction 文件；
- 工作区文件和 Git 仓库；
- 项目知识与 FAISS Memory；
- variables 与 secrets；
- Skills；
- MCP Server 配置；
- 子 Agent 启用状态；
- 文件树注入规则；
- 模型与 Plugin 的项目级配置。

## 目录结构

```text
usr/projects/<project>/
├─ 项目工作文件或Git仓库
└─ .a0proj/
   ├─ project.json
   ├─ instructions/
   ├─ knowledge/
   ├─ skills/
   ├─ memory/
   ├─ variables.env
   ├─ secrets.env
   ├─ mcp_servers.json
   └─ agents.json
```

实际文件名以当前版本实现为准，核心思路是把项目元数据和工作文件放在同一个可迁移工作区。

## 激活Project后发生什么

1. Context 保存项目名；
2. Project 主指令、`AGENTS.md` 和 instruction 文件进入 Protocol；
3. 项目标题、路径和 Git 信息进入 System Prompt；
4. 文件树按深度、数量、行数和 `.gitignore` 规则注入 Extras；
5. 工具工作目录切换到项目路径；
6. Memory 使用项目自己的索引；
7. MCP、Skills、Secrets 和 Plugin 配置按项目解析。

## 文件树为什么要限制

把整个仓库树放进 Prompt 会造成：

- Token 膨胀；
- `node_modules`、构建产物等噪声；
- 文件多时掩盖关键目录；
- 可能暴露不该进入上下文的文件名。

项目通过 `max_depth`、`max_files`、`max_folders`、`max_lines` 和 ignore 规则限制注入。Agent 需要更多信息时，应通过文件工具按需读取。

## Variables与Secrets

- Variables 保存非敏感配置，例如默认区域和报告格式；
- Secrets 保存 API Key 或密码，通过名称在工具中引用；
- Prompt、日志和工具结果应遮蔽密钥值；
- Git Clone Token 只通过 HTTP Header 使用，不写进 URL 或 Git Config。

“值被遮蔽”不等于安全完成。还需要文件权限、密钥轮换、最小权限和审计。

## Project配置的合并

常见作用域：

```text
系统默认
→ 全局用户配置
→ Agent Profile配置
→ Project配置
→ Chat临时覆盖
```

越具体的作用域通常优先级越高，但不同模块必须遵循一致规则。否则 Model、MCP、Skill 与 Plugin 可能各用一套合并方式，导致问题难以定位。

## Project隔离不等于租户安全

Project 是应用层隔离，主要解决上下文和文件组织。企业级多租户还需要：

- 用户认证和项目授权；
- 服务端强制作用域，不能信任客户端提交的项目名；
- 文件系统或容器隔离；
- 按项目的网络与工具权限；
- Secret访问审计；
- 向量索引和日志的租户过滤；
- 删除、备份和数据保留策略。

## 串扰测试

建立两个 Project，并放入故意冲突的信息：

- 同名文件但内容不同；
- 同一问题的不同项目规则；
- 同名 variable/secret；
- 不同 MCP Server；
- 相似但互斥的 Memory；
- 不同 Agent 与 Skill 开关。

切换 Project 后逐项验证 Prompt、工具目录、Memory、MCP、Secrets 和日志。串扰率应为零。
