# 多轮会话与上下文管理

## 为什么Agent更依赖上下文管理

普通问答通常只需要问题和少量历史。Agent 还要携带目标、项目指令、工具说明、执行结果、文件状态、记忆、子任务和错误信息。上下文过少会导致失忆，过多会增加成本、延迟和注意力干扰。

上下文管理的目标不是“塞入尽可能多的信息”，而是让模型在当前步骤看到足够、最新且不矛盾的信息。

## 四类上下文

项目每轮 Prompt 可以按四类理解：

### System

定义长期稳定的角色、行为和工具协议，例如主 Prompt、Agent Profile、Tool 和 MCP 说明。

### Protocol

保存当前聊天需要稳定遵循的信息，例如 Project Instructions 和已加载 Skill。它比普通 Extras 更稳定，不应每轮随意丢失。

### History

保存用户消息、模型回复和工具结果，按时间形成可追溯任务过程。

### Extras

保存当前轮动态计算的信息，例如：

- 相关长期记忆；
- 当前时间；
- Project 文件树；
- 已启动的并行 Job；
- Desktop 状态；
- Agent 信息和工作目录。

把动态环境状态放在 Extras，可以在每轮重新生成，避免长期保留陈旧信息。

## AgentContext与Agent

`AgentContext` 是聊天级运行时，主要保存：

- context id 与名称；
- 创建时间与最后消息时间；
- 当前任务和暂停状态；
- 主 Agent 和正在输出的 Agent；
- Log 与输出数据；
- 当前激活 Project；
- 跨 Agent 共享数据。

`Agent` 则保存具体执行者的 Profile、History、最后用户消息、intervention 和工具数据。一个 Context 内可以先后运行主 Agent 和子 Agent。

## History的分层结构

项目没有把所有消息放在一个线性 list 中，而是分成：

```text
History
├─ Bulks：较早历史的聚合摘要
├─ Topics：已经结束的主题
└─ Current Topic：当前任务的详细消息
```

这种结构让最近内容保留细节，较早内容逐层压缩。

### 压缩顺序

1. 判断 History Token 是否超过 `ctx_length × ctx_history`；
2. 对异常长的单条消息做截断或替换；
3. 对 Current Topic 中间部分做注意力压缩；
4. 对历史 Topic 摘要；
5. 将较早 Topic 合并成 Bulk；
6. 将多个 Bulk 再次合并；
7. 如果仍无法降低，移除最早 Bulk。

压缩循环带有“压缩后 Token 必须下降”的保护，防止模型摘要反而更长导致无限压缩。

## 上下文压缩与长期记忆的区别

| 机制 | 目标 | 数据组织 | 触发方式 |
| --- | --- | --- | --- |
| History压缩 | 当前聊天继续运行 | 按时间和Topic摘要 | 超过上下文预算 |
| Chat Compaction | 主动把整段聊天压成新摘要 | 压缩前备份、压缩后替换 | 用户或API触发 |
| 长期Memory | 跨聊天按语义找回信息 | Embedding + FAISS | 每隔若干轮检索 |

摘要并不自动成为可靠长期事实。长期记忆也不应替代完整的会话日志。

## 持久化与恢复

聊天持久化会序列化：

- `AgentContext` 基本信息与 data；
- Agent 配置、Profile 与 History；
- Log；
- 时间信息和项目绑定。

聊天重新加载后，父子 Agent 原始调用栈可能不存在，因此 `_process_chain()` 会根据 `SUPERIOR` 引用把子 Agent 结果继续传回上级。

## Token预算

上下文预算至少要给以下部分留空间：

```text
模型上下文窗口
= System与工具说明
+ Protocol
+ History
+ Extras
+ 本轮模型输出预算
```

只给 History 设置上限仍可能超窗，因为 MCP 工具说明、Skills 和 Memory 也会增长。更合理的做法是为每一类上下文分配预算，并记录实际 Token 占比。

## 上下文污染

常见污染来源：

- 已经过时的工具结果；
- 与当前 Project 无关的记忆；
- 失败尝试被总结成“成功经验”；
- Skill 在任务结束后仍持续影响行为；
- 同一规则在 System、Project 和 Memory 中冲突；
- 大量低价值日志淹没当前目标。

排查时要分别检查 System、Protocol、History、Extras，而不是只看最后几轮聊天。

## 实际验证建议

建立一组长对话任务，在压缩前后询问：

- 当前目标是什么；
- 已经完成哪些步骤；
- 哪些文件被修改；
- 哪些约束不能违反；
- 当前失败原因是什么；
- 下一步应该做什么。

比较答案正确率，并记录压缩率、额外模型调用、延迟和 Token 成本。
