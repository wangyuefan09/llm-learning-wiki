# Agent基础与运行循环

## Agent是什么

在大模型应用中，Agent 是一个围绕目标持续执行“获取上下文—模型决策—调用动作—观察结果—更新状态”循环的系统。LLM 负责在当前上下文中做决策，工具负责影响或读取外部环境，运行时负责保存状态、控制循环并处理异常。

一个最小 Agent 至少需要：

- **目标或用户指令**：当前要解决什么问题；
- **状态**：已有消息、任务进度和环境反馈；
- **决策器**：通常是 LLM；
- **动作空间**：可调用的工具或子 Agent；
- **观察结果**：工具返回值、错误和环境变化；
- **终止条件**：完成、失败、超限、取消或等待用户。

## Agent、聊天与Workflow

| 形态 | 谁决定下一步 | 状态 | 适合场景 |
| --- | --- | --- | --- |
| 普通聊天 | 用户发一轮，模型答一轮 | 主要是消息历史 | 解释、写作、简单问答 |
| 固定Workflow | 代码或流程图预先决定 | 节点状态明确 | 稳定、可枚举、强合规流程 |
| Agent | 模型根据目标与观察动态决定 | 消息、工具结果、环境和任务状态 | 路径不确定的复杂任务 |

Agent 不代表所有流程都交给模型。稳定的校验、权限、重试、预算和副作用控制应该由代码保证；模型更适合处理开放式理解、选择和生成。

## 通用Agent Loop

```text
while 未结束:
    context = 组装目标、历史、记忆、工具和环境状态
    decision = LLM(context)
    if decision 是最终回答:
        return decision
    action = 校验并执行工具调用
    observation = 收集工具结果或错误
    把 decision 与 observation 写回状态
```

这个循环与 ReAct 的“Reason + Act”思想相近，但工程实现不一定要求模型显式输出完整思维过程。系统真正需要的是可解析的 Action 和可回填的 Observation。

## 项目当前实现

`agent.py` 中的 `Agent.monologue()` 是主循环：

1. 建立本轮 `LoopData`；
2. 调用 `monologue_start`、`message_loop_start` 等扩展；
3. `prepare_prompt()` 组装 Prompt；
4. `call_chat_model_turn()` 调用模型并接收流式 reasoning/response；
5. 把模型回复写入 `History`；
6. `process_llm_result_tools()` 处理原生 function call；
7. 没有原生调用时，`process_tools()` 尝试解析 JSON 工具请求；
8. `_execute_tool_request()` 执行 MCP 或本地工具；
9. 工具结果通过 `after_execution()` 回到 History；
10. 工具要求结束或模型直接给出最终回答时返回。

### LoopData保存什么

`LoopData` 保存当前循环需要的临时状态，例如：

- `iteration`：循环次数；
- `system`：System Prompt 片段；
- `history_output`：历史消息；
- `protocol_persistent/temporary`：稳定或临时协议上下文；
- `extras_persistent/temporary`：稳定或临时附加上下文；
- `current_tool`：当前执行工具；
- `last_response`：上一轮回复，用于重复检测。

它与 `AgentContext` 不同：`LoopData` 面向当前一次任务循环，`AgentContext` 面向整个聊天运行时。

## 如何结束循环

常见终止方式包括：

- 模型返回普通最终文本；
- `response` 工具返回 `break_loop=true`；
- 用户终止或重置任务；
- 错误处理扩展判断任务不可继续；
- 达到步数、Token、时间或成本上限。

项目源码已经实现前四类基础控制，但统一的任务总步数、总 Token 和总耗时预算仍值得补充。只有工具级超时，不足以防止模型在多个工具之间长时间循环。

## 用户干预

Agent 运行时不能假设用户只在任务开始前说话。项目会在模型流式回调、工具执行前后等位置检查 intervention：

1. 保存当前工具已经产生的进度；
2. 把新用户消息写入 History；
3. 中断当前路径；
4. 用新上下文重新进入循环。

这种设计比等待整个任务结束后再处理新消息更适合长任务，但要注意工具是否已经产生不可逆副作用。

## 常见失败模式

- **无限循环**：模型反复调用同一工具或在两个动作间震荡；
- **错误结束**：工具成功但模型仍继续，或任务未完成就回答；
- **格式错误**：模型输出无法解析的工具调用；
- **观察缺失**：工具结果未回填，模型不知道动作发生了什么；
- **状态陈旧**：环境已经变化，Prompt 中仍是旧状态；
- **副作用重复**：重试导致重复发消息、重复写文件或重复提交。

工程上应补充最大步骤、重复调用检测、幂等键、工具结果校验和任务级状态机。

## 个人理解

Agent 的核心不是“模型能调用工具”，而是运行时能否把决策、动作、观察、状态和终止条件连接成一个可控制、可观测的闭环。工具数量增加不等于 Agent 质量提高；没有状态和评估，工具越多反而越容易选错。
